# Защищённая оверлейная P2P-сеть передачи данных

Курсовая работа по дисциплине «Сети и системы передачи информации» (4 курс).  
Тема: **«Защищённая оверлейная сеть передачи данных на основе пиринговых протоколов»**.  
Уровень реализации: **Продвинутый** ($N = 20\text{--}21$ логических узлов, ёмкость бакета $k = 4$, параллелизм $\alpha = 3$, собственный AKE без TLS, луковичные туннели $\ge 3$ хопов, блочная передача файлов с SHA-256, профилирование ретрансляторов).

---

- [**Архитектурная спецификация (docs/architecture.md)**](docs/architecture.md) — детальное описание 7 подсистем, 4 независимых графов сети, итеративного Kademlia-поиска, протокола AKE, луковичной маршрутизации, критериев невырожденности DHT и фасада `NodeFacade`.
- [**Спецификация протокола (docs/protocol_spec.md)**](docs/protocol_spec.md) — бинарный 24-байтовый заголовок кадра, схема флагов, коды 25 типов сообщений и схемы CBOR-сериализации.
- [**Сравнение форматов сериализации (docs/serialization_comparison.md)**](docs/serialization_comparison.md) — инженерное обоснование выбора CBOR (RFC 8949) против MessagePack и JSON.

## 🛠 Технологический стек

- **Язык**: C++20 (`std::span`, spaceship operator `<=>`, concepts, structured bindings)
- **Сетевой I/O**: `boost::asio` / `asio standalone` (асинхронная неблокирующая обработка сокетов)
- **Криптография**: `libsodium` (Ed25519 для цифровых подписей, Curve25519/X25519 для ECDH, ChaCha20-Poly1305 для AEAD, SHA-256)
- **Сериализация**: CBOR (RFC 8949) через библиотеку `nlohmann/json`
- **Конфигурация**: TOML через `tomlplusplus`
- **Логирование**: `spdlog`
- **Тестирование**: `Catch2 v3` (Unit, Negative и Integration тесты)
- **Развёртывание**: Docker, Docker Compose, Linux Network Namespaces

## 📋 Описание этапов разработки

Проект разрабатывается поэтапно в строгом соответствии с [ТЗ](file:///c:/school/4cource/seti/TZ_kursovaya_rabota_2026.md) и [Чек-листом приёмки](file:///c:/school/4cource/seti/Чек-лист%20приёмки%20этапов%20курсовой%20работы.md):

### Этап 1. Сетевой транспорт, идентичность и кадрирование
- **Цель**: Обеспечение надёжного асинхронного обмена кадрами между узлами поверх TCP и криптографическая идентичность.
- **Реализация**:
  - Асинхронный сервер [`TcpListener`](src/transport/tcp_listener.hpp) и сессии [`TcpConnection`](src/transport/tcp_connection.hpp) с очередью записи;
  - Двоичный 24-байтовый заголовок кадра ([`Frame`](src/transport/frame.hpp)): `version`, `type`, `flags`, `request_id` (16B), `payload_length` (4B);
  - Потоковый декодер [`FrameParser`](src/transport/frame.hpp) со скользящим буфером, устойчивый к склейке TCP-пакетов, частичным заголовкам и фрагментации;
  - Жёсткая валидация `MAX_FRAME_PAYLOAD = 65 536` байт до выделения буфера памяти;
  - Долговременная пара ключей Ed25519 ([`Keypair`](src/identity/keypair.hpp)) с сохранением в `node_state_dir`;
  - Детерминированный идентификатор $NodeID = \text{SHA-256}(\text{identity\_public\_key})$;
  - Конфигурационный модуль [`Config`](src/config/config.hpp) на базе TOML.
- **Тесты**: [`test_frame.cpp`](tests/unit/test_frame.cpp) (стресс-тест из 120 кадров со случайным разбиением потока), [`test_node_id.cpp`](tests/unit/test_node_id.cpp) (XOR-расстояние, Ed25519 подписи).

### Этап 2. Kademlia DHT и обнаружение узлов (Node Discovery)
- **Цель**: Реализация распределённой таблицы маршрутизации, итеративного поиска узлов и децентрализованной процедуры bootstrap.
- **Реализация**:
  - Структура [`KBucket`](src/dht/k_bucket.hpp) с фиксированной ёмкостью $k = 4$, LRU-вытеснением контактов и очередью кандидатов на замену (`replacements_`);
  - Таблица маршрутизации [`RoutingTable`](src/dht/routing_table.hpp) на 256 бакетов с определением индекса бакета по первому различающемуся биту XOR-расстояния;
  - Функция `find_closest(target, count)` — сбор и сортировка $k$ ближайших активных контактов;
  - Сериализация RPC-сообщений [`dht_messages`](src/dht/dht_messages.hpp) в компактный CBOR (`FIND_NODE_REQUEST`, `FIND_NODE_RESPONSE`);
  - Конечный автомат [`LookupSession`](src/dht/lookup_engine.hpp) для параллельного итеративного поиска с фактором $\alpha = 3$;
  - Сетевой метод [`Node::async_lookup`](src/node.cpp) с автоматическим установлением соединений к новым найденным узлам;
  - Процедура **децентрализованного Bootstrap**: при старте узел подключается к seed-узлу и выполняет `self-lookup` для заполнения таблицы маршрутизации;
  - Взаимная корреляция RPC-ответов по `request_id` через таблицу отложенных запросов;
  - Защита от спуфинга: узел отклоняет и сбрасывает соединение при несоответствии claimed $NodeID$ и переданного открытого ключа (`E2-2`);
  - Экспорт состояния бакетов в JSON для подтверждения невырожденности (`E2-8`).
- **Тесты**:
  - [`test_k_bucket.cpp`](tests/unit/test_k_bucket.cpp) — проверка переполнения и очереди кандидатов;
  - [`test_routing_table.cpp`](tests/unit/test_routing_table.cpp) — индексы 0..255 и ранжирование по XOR;
  - [`test_lookup.cpp`](tests/unit/test_lookup.cpp) — сходимость итеративного поиска $\alpha = 3$ в графе;
  - [`test_lru_scenarios.cpp`](tests/unit/test_lru_scenarios.cpp) — **два обязательных сценария E2-4**: живой LRU-контакт остаётся в бакете после проверки, недоступный контакт вытесняется кандидатом;
  - [`test_negative_identity.cpp`](tests/negative/test_negative_identity.cpp) — отсечение атак с поддельными ключами (`E2-2`);
  - [`test_dht_integration.cpp`](tests/integration/test_dht_integration.cpp) — сетевой обмен по TCP и работа кластера из 5 узлов после остановки seed-узла (`E2-5`, `E2-7`).

### Этап 3. Хранение записей в DHT (STORE, FIND_VALUE, псевдонимы)
- **Цель**: Распределённое хранение и разрешение записей узлов (`NodeRecord`) и псевдонимов (`AliasRecord`) с гарантией устойчивости к отказу хранителей.
- **План реализации**:
  - Структура подписанной записи `NodeRecord`: владелец, открытый ключ, список адресов, `sequence_number`, метки времени и подпись Ed25519;
  - Разрешение псевдонимов: детерминированный ключ $Key = \text{SHA-256}(\text{"alias:"} \parallel \text{normalize}(alias))$;
  - Репликация записей на $R = 3$ ближайших узлах с кворумом подтверждения $\ge 2$;
  - Контроль времени жизни (TTL = 120–300 с) и автоматическое фоновое переопубликование с интервалом $\text{TTL}/2$;
  - Защита от отката: приём записей строго с возрастающим `sequence_number`;
  - Сохранение доступности записи при отключении 1 из 3 хранителей (`E3-5`).

### Этап 4. Защищённая сессия (Собственный криптографический AKE)
- **Цель**: Полноценная защита межузловых TCP-соединений без использования готового TLS (требование продвинутого уровня).
- **План реализации**:
  - Эфемерный обмен Диффи-Хеллмана на Curve25519 (X25519) для каждой сессии (Perfect Forward Secrecy);
  - Взаимная аутентификация через подпись полного канонического транскрипта долговременными ключами Ed25519;
  - Деривация симметричных сессионных ключей через HKDF-SHA-256 с раздельными ключами для направлений $A \to B$ и $B \to A$;
  - Симметричное AEAD-шифрование полезной нагрузки ChaCha20-Poly1305;
  - Защита от Replay: монотонные 64-битные счётчики пакетов и скользящий кэш уникальных `session_id`.

### Этап 5. Многопереходные туннели и Onion Routing
- **Цель**: Построение многозвенных виртуальных каналов через цепочку промежуточных ретрансляторов с луковичным шифрованием.
- **План реализации**:
  - Маршруты длиной не менее 3 промежуточных ретрансляторов ($\text{Src} \to R_1 \to R_2 \to R_3 \to \text{Dst}$);
  - Послойная инкапсуляция шифрования (каждый релей видит только адрес следующего звена);
  - Пул из не менее чем 3 активных/подготовленных туннелей;
  - Профилирование ретрансляторов (`RelayProfiler`): скользящее среднее EMA задержки (RTT) и успешности, фильтрация подсетей /24 для обеспечения топологического разнообразия;
  - Автоматическое обнаружение сбоев и перестроение туннеля при отключении ретранслятора.

### Этап 6. Прикладные сервисы (E2E Сообщения и Блочная передача файлов)
- **Цель**: Пользовательские сервисы поверх многопереходных туннелей.
- **План реализации**:
  - Сквозное (End-to-End) шифрование прикладных сообщений с гарантией доставки (`APP_ACK`) и дедупликацией;
  - Передача файлов блоками по 48–60 КиБ (гарантированное укладывание в `MAX_FRAME_PAYLOAD = 65 536` байт);
  - Контроль целостности блоков и файла по хэшу SHA-256;
  - Скользящее окно передачи и локальная запись только в выделенную директорию.

### Этап 7. Развёртывание и масштабирование сети ($N = 21$)
- **Цель**: Полномасштабный запуск сети продвинутого уровня и доказательство невырожденности DHT.
- **План реализации**:
  - Оркестрация 21 независимого логического узла в изолированных контейнерах;
  - 4 схемы начальной загрузки (Bootstrap topologies): `star`, `ring`, `tree`, `multi-seed`;
  - Проверка 6 условий невырожденности DHT: отсутствие общего реестра, $\ge 80\%$ узлов знают $< N - 1$ контактов, сохранение связности при падении seed-узла;
  - Сценарий с ограничением IP-достижимости через подсети Docker / `nftables`.

### Этап 8. Эксперименты, эмуляция netem и аналитический отчёт
- **Цель**: Сбор экспериментальных данных, валидация гипотез и построение графиков.
- **План реализации**:
  - Серия из не менее 30 контрольных многопереходных поисков;
  - Эмуляция сетевых задержек и потерь пакетов через Linux `tc/netem`;
  - Автоматический экспорт телеметрии в неизменяемые сырые файлы CSV/JSON;
  - Построение графиков сходимости, задержек, заполнения бакетов и надёжности туннелей.

## 🔨 Сборка из исходников

### Требования
- Компилятор с поддержкой C++20 (GCC ≥ 11, Clang ≥ 13, MSVC 2022)
- CMake ≥ 3.20
- Менеджер пакетов `vcpkg`

### Инструкция по сборке

```bash
# 1. Установка vcpkg (если не установлен)
git clone https://github.com/microsoft/vcpkg.git
./vcpkg/bootstrap-vcpkg.sh  # Для Windows: .\vcpkg\bootstrap-vcpkg.bat

# 2. Конфигурация и сборка проекта
cmake -B build \
  -DCMAKE_TOOLCHAIN_FILE=./vcpkg/scripts/buildsystems/vcpkg.cmake \
  -DCMAKE_BUILD_TYPE=Release
cmake --build build

# 3. Запуск всего набора автоматических тестов (Unit, Negative, Integration)
cd build && ctest --output-on-failure

# 4. Запуск узла вручную
./build/p2p_node --port 9000 --data-dir ./node_0_data --log-level info
```

## 📊 Параметризация конфигурации

Все системные параметры вынесены в TOML-конфигурации и изменяются без перекомпиляции исходного кода:

| Секция | Параметр | Значение | Описание |
|---|---|:---:|---|
| `dht` | `k_bucket_size` | `4` | Максимальная ёмкость одного $k$-bucket'а |
| `dht` | `alpha` | `3` | Параметр параллелизма итеративного поиска |
| `dht` | `replication` | `3` | Фактор репликации записей ($R$) |
| `dht` | `ttl_seconds` | `180` | Время жизни записей в DHT |
| `tunnel` | `min_relay_hops` | `3` | Минимальное число промежуточных ретрансляторов |
| `tunnel` | `pool_size` | `3` | Количество одновременно поддерживаемых туннелей |
| `transport` | `max_frame_payload`| `65536` | Максимальный размер полезной нагрузки кадра |
